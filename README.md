# makeRowing

FTMS 로잉머신에 연결해서 돌아가는 3D 로잉 게임. iPad 1대 + 로잉머신 1대 구성.

EXR과 비슷한 컨셉 — 실제 노 젓는 속도에 맞춰 3D 아바타가 젓고, 코스를 따라 전진합니다.

## 빠르게 실행

```bash
npm install
npm run dev
```

로잉머신 없이 둘러보려면 **"시뮬레이터로 둘러보기"**. 레이스 화면 좌하단 강도 슬라이더로
아바타 반응을 확인할 수 있고, 우상단 **◳** 버튼으로 카메라를 바꿀 수 있습니다.

## iPad에서 실기기 연결

iPadOS Safari는 **Web Bluetooth를 지원하지 않습니다.** (Apple이 구현을 거부했고,
iOS의 모든 브라우저가 WebKit을 쓰므로 Chrome을 깔아도 동일합니다.)
App Store에서 **Bluefy** 브라우저를 받아서 접속하세요.

Web Bluetooth는 **HTTPS(secure context)** 를 요구하므로 `http://192.168.x.x:5173`
같은 LAN 주소로는 BLE가 동작하지 않습니다. 터널을 쓰세요:

```bash
npm run dev              # 터미널 1
npm run tunnel           # 터미널 2 → https://xxx.trycloudflare.com
```

`cloudflared`가 없으면 `brew install cloudflared` (또는 `ngrok http 5173`).
나온 HTTPS 주소를 iPad의 Bluefy에서 열면 됩니다. 핫 리로드도 그대로 동작합니다.

> 앱스토어 배포까지 갈 거라면 Capacitor로 감싸고 `@capacitor-community/bluetooth-le`로
> 갈아타면 됩니다. 게임 코드는 그대로 재사용됩니다.
> 이때 `Info.plist`에 `NSBluetoothAlwaysUsageDescription`을 반드시 넣어야 합니다.

## 페이스 보트와 목표 속도

페이스 보트(회색)는 **"최소한 이 속도는 타야 한다"**는 기준선입니다. 코스 선택 화면의 목표 페이스
(가볍게 2:30 / 스테디 2:15 / 강하게 2:05 / 레이스 1:55 / 전력 1:45)에 구간 강도를 곱한 속도로 달립니다.

카운트다운(준비 → 3·2·1 → 시작)이 끝나도 **첫 스트로크가 들어올 때까지** 시계·페이스 보트·고스트가 함께
기다립니다. 출발은 "스트로크가 새로 완료됐다" 또는 "속도가 직전보다 빨라졌다"로만 판정합니다 —
관성으로 도는 플라이휠(거리는 늘고 페이스는 느려짐)이나 PM5처럼 마지막 값을 붙들고 보내는 콘솔에는
속지 않습니다. 대기 중 쌓인 관성 거리는 출발선에서 0으로 다시 잽니다. 노를 놓으면 배도 멈춥니다:
페이스·파워 0이 2.5초 이어지거나 거리가 3초 동안 안 늘면 정지로 봅니다. 시뮬레이터는 강도 슬라이더를
맨 왼쪽에 두면 노를 놓은 상태(플라이휠 관성 포함)를 흉내 냅니다.

레이스 화면 가운데의 **목표 게이지**가 이 속도를 직관적으로 보여줍니다. 흰 선이 목표 페이스, 막대가 지금
페이스입니다. 선에 못 미치면 붉게 깜빡이고("더 세게 당기세요"), 넘으면 초록이 됩니다. 계산은
`src/game/paceGauge.ts`에 있습니다.

## 로어 모델

`src/three/rig.ts`는 외부 모델 파일 없이 매 프레임 관절 **위치**를 계산해 메시를 맞춥니다.
자연스러워 보이게 만드는 요소는 대부분 실제 로잉 동작에서 왔습니다.

- **팔 길이가 노 각도를 정합니다.** 예전에는 손잡이의 X좌표만 정해 놓아서 팔꿈치가 늘 100°쯤 굽은 채
  다리 드라이브 내내 팔로 젓는 것처럼 보였습니다. 지금은 `solveSweep()`이 "어깨에서 팔 길이만큼 떨어진
  손잡이 위치"를 원-구 교차로 풀어 캐치에서 팔이 곧게(159°) 펴집니다.
- **엉덩이 관절이 시트 위에 있습니다.** 발보다 12cm 높아 캐치에서 정강이가 수직으로 섭니다.
  예전에는 4cm뿐이라 무릎이 가슴을 뚫고 올라왔습니다.
- **척추가 두 마디**(허리·등)라 캐치에서 등이 둥글게 말리고 피니시에서 가슴이 열립니다.
- **블레이드가 드라이브에 서고 리커버리에 눕습니다**(페더링). 축을 명시적으로 세워야 합니다 —
  `place()`는 노 축 둘레의 회전을 정하지 못해 방향마다 제멋대로 굴러갑니다.
- 왼손이 오른손 위로 지나가고(노받이 1.5cm 차이), 캐치에서 뒤꿈치가 들리며, 호흡에 따라 가슴이
  부풀고 어깨가 내려앉습니다. 눈은 2.5~5초마다 깜빡이고, 보트마다 seed가 달라 셋이 동시에 깜빡이지 않습니다.
- 팔다리 양 끝 반구의 **중심**이 관절에 오므로 관절 구를 따로 얹지 않아도 이음매가 매끄럽습니다.

## 날씨와 풍경

날씨는 **코스 구간마다 하나로 고정**됩니다 (`profileSections()` — 인터벌은 스텝, 웨이브는 반주기,
스테디·빌드는 5분 단위). 구간이 바뀔 때만 18초에 걸쳐 다음 날씨로 넘어갑니다.

여섯 가지 중 밝은 날씨(쨍한 맑음 · 햇빛이 물에 반짝이는 가을 하늘 · 황금빛 오후)가 2/3 이상이고,
바람·비·눈은 가끔 끼어듭니다. 가을 하늘에서는 나무가 단풍으로 물들고, 비가 그친 뒤 맑아지면 무지개가 뜹니다.
개발 중에는 `?weather=아무값`으로 날씨 일정을 고정할 수 있습니다.

강변에는 수종 6가지 나무, 포즈·복장이 다른 응원객, 오리·백조, 오두막·저택·선착장·텐트·깃발·벤치·가로등 등
소품 17종이 흩어져 있고, 하늘에는 구름·열기구·비행선·새떼·달이 떠 있습니다. 코스에는 교회·연립주택·목조 다리·
현수교·관중석·등대 같은 랜드마크가 추가되었습니다. 소품은 정점 색을 구워 메시 하나로 합쳐 draw call을 아낍니다.

## 코스

16종. **길이가 아니라 페이스가 얼마나 오르내리는지**로 묶여 있습니다.
길이는 카드에 붙어 있고, 카드마다 페이스 범위(예: `94~106%`)와 곡선 그래프가 표시됩니다.

### 완만 — 페이스가 거의 일정하거나 한 방향으로만 천천히 변합니다

| 코스 | 시간 | 유형 | 패턴 |
|---|---|---|---|
| 템스 이지 | 20분 | 스테디 | 일정 |
| 헨리 스테디 | 30분 | 스테디 | 일정 |
| 템스 잔물결 | 30분 | 웨이브 | 10분 주기 ±3.5% |
| 헨리 롱 빌드 | 30분 | 빌드 | 0.94 → 1.06 단조 상승 |
| 헨리 크루즈 | 30분 | 인터벌 | 5분 크루즈(×1.06) / 1분 이지(×0.95) × 5 |
| 보스반 스테디 | 40분 | 스테디 | 일정 |
| 보스반 네거티브 | 40분 | 빌드 | 0.95 → 1.08 단조 상승 |
| 보스반 롱 블록 | 40분 | 블록 | 10분 블록 4개, 0.96 → 1.06 → 0.98 |

### 변화 있음 — 구간마다 강약이 오갑니다

| 코스 | 시간 | 유형 | 패턴 |
|---|---|---|---|
| 템스 웨이브 | 30분 | 웨이브 | 5분 30초 주기 ±6% |
| 헨리 인터벌 | 30분 | 인터벌 | 3분 강(×1.10) / 2분 회복(×0.90) × 6 |
| 보스반 웨이브 | 40분 | 웨이브 | 8분 주기 ±8% |
| 보스반 피라미드 | 40분 | 피라미드 | 5분마다 한 계단, 0.94 → 1.10 → 0.94 |

### 고강도 — 기본 코스가 편해졌을 때

| 코스 | 시간 | 유형 | 패턴 |
|---|---|---|---|
| 템스 스프린트 | 20분 | 스프린트 | 40초 전력(×1.28) / 80초 회복(×0.84) × 10 |
| 보스반 쓰레숄드 | 20분 | 쓰레숄드 | 4분(×1.15) / 1분 회복(×0.86) × 4 |
| 헨리 20분 테스트 | 20분 | 테스트 | 20분 내내 ×1.12 고정 |
| 헨리 레이스 시뮬 | 30분 | 레이스 | 스타트(×1.32) → 본 페이스(×1.12) → 스퍼트(×1.24) × 5 |

### 그룹은 자동으로 정해집니다

`profileOscillation()`이 **방향이 뒤집히는 지점의 최대 낙차**를 재고,
0.115 이하면 '완만'입니다. 단순히 최대~최소 범위를 쓰지 않는 이유는,
처음부터 끝까지 한 방향으로만 오르는 빌드 코스는 범위가 넓어도 오르내림이 0이기 때문입니다.
(헨리 롱 빌드는 범위가 94~106%로 넓지만 오르내림은 0이라 '완만'에 들어갑니다.)

코스를 추가하면 그룹은 알아서 잡힙니다.

### 강도 표기

강도(`intensity`)는 **속도 배율**입니다. 1.10이면 기준 페이스보다 10% 빠름
(스플릿은 역수라 `split = baseSplit / intensity`).

목표 페이스를 고르면 각 코스의 예상 거리가 계산됩니다 —
평균 강도가 1이 아닌 코스(인터벌·피라미드)는 그것까지 반영합니다.

**구간 전환은 기본 12초에 걸쳐 넘어갑니다**(`DEFAULT_RAMP`). 짧으면 페이스 보트 속도가
뚝뚝 끊겨 따라가기 나쁩니다. 구간이 짧으면 램프가 구간을 다 잡아먹지 않도록 30%로 제한되고,
`rampSec`으로 코스마다 더 느긋하게 잡을 수 있습니다(롱 블록은 40초).

**코스 추가**는 `src/game/courses.ts`의 `COURSES` 배열에 넣으면 됩니다.
새 유형이 필요하면 `src/game/profile.ts`의 `PaceProfile`에 종류를 추가하세요.
현재 종류: `steady` / `wave` / `ramp`(단조 변화) / `intervals`.

레이스 중에는 프로파일대로 **페이스 보트**가 빨라졌다 느려집니다.
HUD 상단의 `목표`가 지금 요구되는 스플릿, 그 아래 배지가 현재 구간과 남은 시간입니다.

## 5분 피드백

5분마다 직전 구간의 실제 스플릿을 그 구간이 요구한 목표와 비교해 한 줄 코칭을 띄웁니다.
6초 뒤 자동으로 닫히고, 탭하면 바로 닫힙니다. 게임은 멈추지 않습니다.

목표 대비 차이(초)로 톤이 갈립니다 — `src/game/feedback.ts`:

| 차이 | 톤 | 예시 |
|---|---|---|
| 4초 이상 빠름 | great | "아주 좋습니다" |
| 1.5~4초 빠름 | good | "잘 하고 있어요" |
| ±1.5초 | onpace | "정확히 목표 페이스" |
| 1.5~4초 느림 | push | "조금만 더" |
| 4초 이상 느림 | behind | "더 빨리 타야 해요" |

문구는 톤마다 3개씩 돌아가고, 다음 구간이 바뀌면 예고를 덧붙입니다.

> 5분을 기다리지 않고 확인하려면 `?checkpoint=20` 을 붙이세요 (20초마다 뜹니다).

## 기록

세션이 끝나면 localStorage에 저장됩니다. 코스별 개인 최고(거리 기준)에 **PB** 배지가 붙고,
행을 탭하면 스플릿 추이 곡선이 펼쳐집니다. 1분 미만이거나 50m 미만인 세션은 저장하지 않습니다.

곡선은 초 단위 기록을 1분 단위로 솎아서 저장하는데, 평균이 아니라 **중앙값**을 씁니다 —
출발 직후의 비정상적으로 큰 스플릿에 첫 점이 끌려가지 않게 하려는 것입니다.

서버가 없으므로 브라우저 데이터를 지우면 함께 사라집니다.

## 아바타 스트로크 동기화

BLE는 1~2Hz인데 화면은 60fps입니다. `StrokeEngine`(`src/game/stroke.ts`)이 이 간극을 메웁니다:

- `strokeRate`(spm)로 매 프레임 위상을 굴려서 부드럽게 만들고 **(외삽)**
- `strokeCount`가 증가하면 실제로 한 스트로크가 끝난 것이므로 위상을 catch로 리셋 **(보정)**

자세는 실제 로잉 시퀀스를 따릅니다 — 드라이브는 **다리 → 몸통 → 팔**, 리커버리는 그 역순.
드라이브가 사이클에서 차지하는 비율도 레이트에 따라 변합니다(저레이트 1:2 → 레이스 1:1).

3D 리그(`src/three/rig.ts`)는 관절 **위치**를 계산한 뒤 캡슐 메시를 두 점 사이에 맞춥니다.
다리와 팔은 2뼈 IK로 풀어서 발이 발판에, 손이 노 손잡이에 정확히 붙습니다.

노는 노받이를 받침으로 하는 **지렛대**로 모델링했습니다. 손잡이 위치만 정하면
블레이드 각도가 저절로 따라오고, 손을 올리면 블레이드가 내려가 물에 잠깁니다 — 실제와 같습니다.

### 아바타 손보기

| 원하는 것 | 건드릴 곳 |
|---|---|
| 상체 숙임/젖힘 각도 | `stroke.ts`의 `CATCH_LEAN` / `FINISH_LEAN` |
| 드라이브·리커버리 순서와 타이밍 | `stroke.ts`의 `pose()` 안 `seg(t, a, b)` 구간 |

| 노 길이·리거 위치 | `rig.ts`의 `LOCK` / `INBOARD` / `OUTBOARD` |
| 블레이드가 잠기는 깊이 | `rig.ts`의 `PHI_DRIVE` / `PHI_RECOVERY` |
| 카메라 | `view.ts`의 `CAMERAS` 배열 |

### 카메라

레이스 화면 우상단 **◳** 로 전환합니다.

| 프리셋 | 보이는 것 |
|---|---|
| **정면** (기본) | 로어의 뒤통수. 지나온 코스가 뒤로 멀어진다 |
| 쿼터 | 진행감과 스트로크 동작의 절충 |
| 추격 | 수로가 소실점까지 뻗는다 |
| 사이드 | 노 젓는 동작이 가장 잘 보인다 |

> 로어는 진행 방향의 **반대**를 보고 앉습니다. 그래서 뒤통수가 보이려면 카메라가
> 뱃머리 쪽에서 뒤를 돌아봐야 하고, 그 대가로 앞으로 올 코스 대신 지나온 코스가 보입니다.
> 이 둘은 동시에 성립하지 않습니다 — 앞이 보이는 구도를 원하면 '추격'을 쓰세요.

## 실기기 연결 시 먼저 볼 것

FTMS는 표준이지만 **기기마다 보내는 필드가 다릅니다.** 처음 연결하면
`src/ble/connection.ts`의 `DEBUG_RAW`를 `true`로 바꾸고 콘솔에서 원본 바이트를 확인하세요.

특히 주의할 두 가지:

1. **flags의 bit 0은 의미가 반대입니다.** 다른 비트는 "1이면 필드 있음"인데 bit 0만
   "0이면 strokeRate/strokeCount 있음"입니다. 여기서 오프셋이 통째로 밀리는 게
   FTMS 파서 버그의 대부분입니다. `rowerData.test.ts`에 이 케이스가 들어있습니다.
2. **필드 순서는 고정, 존재 여부는 가변**입니다. 오프셋 하드코딩 금지.

기기가 `totalDistance`를 주면 그걸 정답으로 삼고 화면은 그쪽으로 수렴시킵니다
(`BoatTracker`). 안 주면 파워에서 속도를 적분합니다.
